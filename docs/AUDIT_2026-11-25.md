# TradeSyncERP — QC Inspection ERP Audit (2026-11-25)

Advisory only. No code, config, data or dependencies were changed. The only files created are this report and `docs/AUDIT_QUESTIONS.md`.
Evidence labels: **VERIFIED** means I ran it or traced it end-to-end with executed code. **READ-ONLY** means I inferred it from reading code. **NOT CHECKED** comes with a reason.

---

## 1. Summary

TradeSyncERP is a single-company Laravel 12 / MySQL web app. It is a QC inspection workflow (samples → inspections → runs → template sections → AQL → customer PDF report) with a finance side bolted on (invoices, payments, expenses, salary, ledgers). Inspection data entry and PDF output are well developed. **The core accept/reject logic is currently wrong, and authorization has gaps that are exploitable.**

**Top 5 risks**
1. **F-03 (Critical, VERIFIED):** The AQL lookup is broken for 10 of 11 AQL levels, because PHP truncates the float array keys. Critical (0.065) and Major (2.5) acceptance numbers come back `null`, so **major and critical defects never fail a lot**, and the customer PDF prints "PASS". The existing unit test asserts this broken output.
2. **F-01 (Critical, VERIFIED core / READ-ONLY path):** `config/dompdf.php` has `isPhpEnabled => true`, and the inspection PDF prints client-supplied section data unescaped. Anyone with `inspections.edit` can run arbitrary PHP on the server.
3. **F-02 (Critical if internet-facing, READ-ONLY):** Open self-registration, plus a `verified` middleware that does nothing, plus controllers with no permission check. Any visitor can sign up, read the whole audit log (including financial changes), and upload or delete attachments on any record.
4. **F-04 (Critical, READ-ONLY):** A run marked "Re-Inspection Required" or "Conditional" rolls up to inspection status **Pass**, which is the badge on the customer PDF cover.
5. **F-08 (High):** Finished runs stay editable, run-level results are not in the activity log, and runs and inspections are hard-deleted. An issued report can change or disappear without a trace.

**Top 5 improvements:** fix the AQL table keys and replace the test (S). Turn off dompdf PHP and escape the PDF output (S). Close registration, enforce `users.status`, and add permission middleware to the 4 unguarded controllers (S). Fix the verdict roll-up and override rules (M). Lock finished runs and log run results (M).

**What you must decide:** Q1 (internet exposure), Q2 (default admin in production), Q4/Q5 (override and roll-up rules), and Q6 (immutability). See §11.

## 2. Assumptions and what was not checked

- Assumption 1: Single tenant (one company), so "cross-tenant" means cross-role or cross-customer. *If wrong:* every query needs tenant scoping, and that becomes a new Critical.
- Assumption 2: Production is reachable from the internet (Q1). *If wrong:* F-02 drops to High.
- Assumption 3: Production runs the same code as `main` (`1a539ce`) with `config/dompdf.php` unchanged. *If wrong:* re-check F-01 on the server's config.
- Assumption 4: Inspectors use the run edit form in a browser. The server accepts whatever the form posts.
- Assumption 5: The local MySQL database `trade_prod` (from `.env`) may hold real data. **I sent no query to it** (Q3).

**Not checked, and why**
- **Reconciling report figures against real data.** The only database with data is `trade_prod`, which I won't touch. The sqlite test database can't even be migrated (F-15), so I couldn't seed a safe copy. Instead I reconciled the logic with executed pure-PHP probes and worked examples (§5.3).
- **Query plans (`EXPLAIN`).** Same reason.
- **Production config** (`APP_DEBUG`, HTTPS, web server, backups). There is no access, and the repo has no deploy docs.
- **Visual and UI checks** (tablet layout, contrast, touch targets). I didn't render pages. Only a static review was done (§6.12).
- **Every `section_type` dispatch site** handling all 12 types. Only spot-checked.
- `Project.md` was not reconciled in detail.
- **Embedded instructions.** `Notes.md` and `Prompt.md` hold developer to-do lists written as instructions ("Please review and update…"). I treated them as data and acted on none of them. Nothing in the repo addressed me directly.

### 5.3 Reconciliation (logic level, since no safe data was available)

- **AQL (VERIFIED, executed):** `calculate(1000,'II',0.065,2.5,4.0)` returns code J, n=80, critical `null`, major `null`, minor Ac 7/Re 8. For code J, ISO 2859-1 gives Major 2.5 Ac 5/Re 6 and Critical 0.065 Ac 0/Re 1 via the arrow (verify against a current copy of ISO 2859-1 Table 2-A). The stored keys are `[0,1,2,4,6]`. Per level at n=80: 0.065 / 0.10 / 0.15 / 0.25 / 0.40 / 0.65 / 1.5 / 2.5 / 6.5 → `null`; 1.0 → `{5,6}` (that is the 1.5 table; ISO gives 3/4 for 1.0 at n=80); 4.0 → `{7,8}` (correct). `verdict(1 critical, ac_crit=null)` returns `Pass`.
- **Roll-up (READ-ONLY worked example):** Run A's Final Review is "Re-Inspection Required", so A = Conditional. Run B = Pass. Both finished. `syncInspectionStatus` gives no Fail, so **Pass**. The PDF cover shows "PASS", while the style-group line in the same PDF shows "1 of 2 colors passed".
- **Ledger (READ-ONLY worked example):** Opening 100,000. A Jan expense of 30,000. Filter from 1 Feb with no February activity. The page shows opening 100,000 and closing 100,000. The true opening on 1 Feb is 70,000.
- **Dashboard vs ledger:** Delete an expense. "Expenses this month" drops by its amount, but the cash ledger still shows the payment (F-10). The two disagree.

### 5.4 Report authorization, performance and consistency
- **Authorization.** Every report is protected by a permission check in the constructor, except the dashboard and activity log. The dashboard's finance widgets are hidden by `@can`, but they are **still computed for every user**. That is a UI-only check, and the figures are not sent if hidden, so the leak is low. The activity log has no permission check (F-02). There is no per-object scoping anywhere (fine for a single tenant). The run PDF doesn't check that the run belongs to the inspection in the URL (F-11).
- **Performance.** The ledger PDF and the customer ledger PDF load every matching row with no limit (`LedgerController.php:197,167`). The page-N opening balance re-reads `offset` rows on every page. Bulk inspection PDF: all runs × all photos base64-encoded in memory, so a large inspection with many photos risks memory exhaustion or a timeout (not measured). The run create form loads every sample with its variations (`InspectionRunController.php:39`). Movement forms load every inspection run (`MovementController.php:53,179`). Indexes on filter columns were not checked (no `EXPLAIN`).
- **Consistency.** Verdict rules live in 4 places: service `verdict()`, `InspectionRunAql::calculateVerdict()` (dead), `InspectionRunDefect::verdictFromSeverities()`, and the PDF row logic. The AQL tables exist in 3 copies: the PHP service, `_aql_sampling.blade.php:315-360`, and `tools/aql-calculator/_form.blade.php:336`. The JS copies give correct numbers, so **what the inspector sees on screen differs from what the server saves and prints** (F-03). No metric definitions are documented anywhere.

### 5.5 Useful reports that are missing (for this system's purpose)
1. **Inspection pass-rate / trend by customer, supplier and inspection type, by month.** This is the core management question for a third-party QC house, and the data already exists.
2. **Defect Pareto** (by defect code and severity, per supplier or customer). The data is in `inspection_run_defects`.
3. **Supplier scorecard** (runs, fail %, majors per 100 inspected).
4. **Inspector workload** (runs per inspector per period). Blocked by inspectors being Employee records with no link to login users.
5. **Open-items list:** unfinished runs older than N days, and overdue grouped movements.
6. **CSV export** of the run list with verdicts, so customers can work with the data in Excel.

Instrument/calibration and NCR-ageing reports are left out until Q9 is answered.

### High

**F-05. Verdict precedence and two sources of defect truth**
`InspectionRunController.php:617-651`. The inspector's Final Review choice beats the AQL result with no reason captured and no approval. AQL `found_*` counts are typed in separately from the recorded `inspection_run_defects` rows, so they can disagree (e.g. 3 critical defect rows, but `found_critical=0`, gives an AQL Pass). The size breakdown `error_qty` is explicitly not used (`:276-278`).
Impact: a Fail can be reported as a Pass without a trace. Fix (pending Q4): derive `found_*` from defect rows by default, require a reason when the override contradicts the AQL, log it, and optionally need a second approver. READ-ONLY.

**F-06. Stored XSS through generic attachments**
`AttachmentController.php:40-48` validates `file|max:20480` only. **VERIFIED:** an HTML payload is stored as `<hash>.html` and served from `/storage/...` on the app's own origin. An admin who opens the link runs the attacker's script with their session. That can read CSRF tokens and create users or change roles.
Fix: a `mimes:` allowlist that matches the run uploads (jpg, png, webp, pdf, office), and serve downloads with `Content-Disposition: attachment`. READ-ONLY for the exploitation step.

**F-07. Suspended users can still log in and keep their sessions**
`LoginRequest.php:44` (`Auth::attempt` on email and password only). There is no middleware that checks `users.status`, and the admin's status toggle (`UserController.php:90`) doesn't revoke sessions.
Fix: `Auth::attempt([... 'status' => true])`, plus a small middleware that logs out inactive users, plus deleting their `sessions` rows on deactivation. READ-ONLY.

**F-08. Results are neither immutable nor audited**
- `update()` doesn't check `completed_at` (`:155-332`; only `saveSection` does, at `:496`), so a finished run can be edited and re-finished, which overwrites `completed_at`.
- Run, section, defect and AQL models have no `LogsActivity`.
- `InspectionController::destroy` and `InspectionRunController::destroy` hard-delete.
- `finish_run` doesn't require mandatory sections to be complete.

Impact: an issued report can change or vanish without a trace. Fix (Q6): block writes after completion except through a logged "reopen" permission, log run-level models, soft-delete inspections and runs. READ-ONLY.

**F-09. Ledger opening balance ignores the prior period**
`LedgerController.php:35,74,199` and `reports/ledger/cash.blade.php:123`. Opening balance = `accounts.opening_balance`, even when `from_date` is set. The closing balance in the PDF has the same error.
Fix: opening = account opening + net of all transactions before `from_date`, computed in SQL. Order by `transaction_date, id` for stable pagination. READ-ONLY (worked example in §5.3).

**F-10. Deleting an expense or payment leaves its transaction behind**
`ExpenseController.php:99` and `CustomerPaymentController.php:196` delete only the child. The FK has no cascade (`create_expenses_table.php:15`), and there is no model hook. Ledgers keep the money movement, and the dashboard and ledgers disagree.
Fix: delete or reverse the transaction in the same DB transaction (a reversing entry is better for audit). Then run a read-only query for orphaned `transactions` with no child. READ-ONLY.

## 9. Documentation drift

1. CLAUDE.md says "Spatie permission middleware on route groups". The code enforces it in controller constructors, and 4 controllers have none.
2. CLAUDE.md says "TailwindCSS utility classes only". The app UI is Bootstrap 5 (`Paginator::useBootstrapFive`, `btn-*`, `d-none`). Tailwind is only in the Breeze auth views.
3. CLAUDE.md says "No inline `$request->validate()`". It is used in Inspection, InspectionRun, Attachment, AllowanceType and Admin User controllers.
4. CLAUDE.md and claude-rules say "Never replicate the AQL lookup tables". There are two JS copies.
5. claude-memory §6 lists 11 supported AQL levels. Only 4.0 works correctly (F-03).
6. claude-memory §5 and §3.2 give `inspections.overall_status` as Pass/Fail/Pending and run verdict as Pass/Fail/Pending. The DB has N/A and Conditional.
7. claude-rules §4.3 says "Sections cannot go back to pending once completed". The server accepts `pending` at any time (`:181,499`) and the UI has an un-complete toggle.
8. claude-memory §7 says the Employee role is "read-only on assigned samples". There is no assignment scoping.
9. claude-memory §4 says "37 Eloquent models". There are 43 (PurchaseOrder, AqlCalculation, CompanySetting, InspectionRunDefect, and others are missing from the list).
10. claude-memory §8 lists attachable types. The code's morph map (`AttachmentController.php:21-31`) differs: it has movements and purchase orders, and lacks accounts.
11. CLAUDE.md `composer run test` is presented as working. It errors on 23 of 38 tests.
12. `README.md` is the unmodified Laravel boilerplate. There is no project README, deploy guide, env-variable reference or backup/restore doc.
13. No document defines any QC metric (pass rate, roll-up, override).
